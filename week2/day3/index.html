A judge-shaped reward

Same GRPO loop as week 1. The only new part is the reward function, and the new risk that comes with it: the model gets better at pleasing the judge rather than at the task.

The task and the rubric

The model reads a news article (truncate to ~400 words to keep prompts short) and writes a summary of at most 50 words. A news-summary dataset with human-written highlights works well, for example CNN/DailyMail (fields article and highlights); the highlights are the reference.

Call it like any OpenAI-style endpoint:

from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

def judge_fn(prompt, completion):
    try:
        r = client.chat.completions.create(
            model="Qwen/Qwen2.5-3B-Instruct", temperature=0, max_tokens=300, timeout=60,
            messages=[{"role": "user", "content": build_judge_prompt(prompt, completion, RUBRIC)}])
        return parse_score(r.choices[0].message.content)   # Day 1 code
    except Exception:
        return None                                        # counted as a failure

Commands and flags change between vLLM and TRL versions; check the docs for the versions you install. Any judge you can reach through an API works the same way.

3

The reward function

  • Scale the 1–10 score to 0–1: (score − 1) / 9.
  • Hybrid: 0.8 × judge + 0.2 × length_ok. Code checks what code can.
  • Failures (timeouts, no score) get the batch's mean judge score, so they barely move the policy. Count them; above a few percent, fix the judge prompt before training.
  • Cache by (prompt, completion). Duplicate answers are common in a group.
  • Parallelize: send a batch's judge calls with a thread pool (e.g. 16–32 workers) instead of one by one.
reward_fn, stats = make_judge_reward(judge_fn, max_words=50, w_judge=0.8, w_len=0.2)
trainer = GRPOTrainer(model=model, reward_funcs=[reward_fn], args=config, train_dataset=ds, ...)
4

Overoptimization: the proxy and the gold

The training judge is a proxy for what you want. Gao, Schulman and Hilton (2022) measured this with reward models: as optimization against a proxy continues, the true ("gold") score rises, peaks and then falls. Goodhart's law, measured.

  • Evaluate with a held-out judge you never train on: a different, stronger model family, or your own labels on a small set.
  • Training score up, held-out score down → you're overoptimizing.
  • Save a checkpoint every 50 steps and pick by held-out score, not training reward. A KL penalty or stopping earlier slows the drift.
  • Baseline first: score the base model with the held-out judge, then compare checkpoints question by question (week 1, Day 6).

8

Glossary

Proxy reward
The score you train on; it stands in for what you really want.
Gold reward
What you really want, measured as carefully as you can.
Overoptimization
Pushing the proxy so hard that the gold reward gets worse.
Goodhart's law
When a measure becomes a target, it stops being a good measure.
Hybrid reward
A weighted mix of code checks and a judge score.
Held-out judge
A different judge you never train on, used only to evaluate.
vLLM server
Runs a model behind an OpenAI-style web API for fast generation.
dtype half
16-bit floats; what T4 GPUs support.
Cache
Remembering judge results so duplicates aren't graded twice.
Thread pool
A set of workers that send many judge calls at once.
Checkpoint
A saved copy of the model during training.
